# 🐛 B-168: 极端断电/进程中断引发的文件物理损坏风险

## 1. 现象 (Symptoms)
如果路由器在执行更新脚本替换文件 (`cp -f /tmp/xxx /etc/ssrplus/xxx`) 的瞬间刚好遭遇物理断电，或者由于其他系统级 OOM killer 意外杀死了正在执行 `cp` 命令的进程，会导致闪存硬盘中的原有有效路由规则文件被「阶段性截断损坏」或彻底变成 0 字节。由于 `cp -f` 的运作方式是先打开清空目标文件（以只写的 `O_TRUNC` 模式 open），然后再慢慢流式写入新内容（`write` 调用）。处于中间态被中断时，目标文件即永久破损。这种风险不仅威胁闪存上的持久化文件，同样也会导致 `/tmp` (tmpfs 内存盘) 上的文件在被替换时，如果刚好被 `dnsmasq` 进程读取，就会读到不完整的数据导致 `dnsmasq` 语法错误启动崩溃！

## 2. MECE 问题树分析 (Root Cause Analysis)

### 2.1 层次定义
- **表层症状**: 物理断电/强杀后，重启发现科学上网失效，配置全空或者乱码；或者 dnsmasq 启动失败报错 config syntax error。
- **根本错误**: 脚本更新替换文件时直接执行 `cp -f 源 目标`。Unix 系统的跨/同文件系统普通拷贝绝非原子操作 (Atomic Operation)。
- **根本原因**: `cp` 等效于 `open(O_TRUNC) -> write(...) -> close()`。非原子操作在执行一半时中断，会导致数据灾难。
- **根本目标**: 确保配置文件的写入具有原子性，在任何中断场景下实现「要么全旧，要么全新」的 0% 中间态损坏。

## 3. 假设驱动与验证测试
- **假设 1 (H1)**：`mv` 在同一文件系统下调用底层 `rename(2)` 系统调用，POSIX 保证它是原子的。
  - **验证**: `rename(oldpath, newpath)` 仅涉及 inode 指针切换。只要新文件完全写好再 `rename`，就绝对不会发生损坏。
- **假设 2 (H2)**：`/tmp` 到 `/etc` 是跨文件系统，直接 `mv` 会退化为 `cp + rm`，依然非原子。
  - **验证**: 是的，必须先将文件 `cp` 到目标目录所在的同一文件系统下作为 `.tmp` 后缀的安全缓冲区，然后再同级 `mv`。

## 4. 修复方案 (Shadow-folder atomic switches)
我们使用标准的“影子替换法”（Atomic Switches）。

### 4.1 代码实现
```lua
-- 改进前: (灾难中间态风险)
luci.sys.exec("cp -f /tmp/ssr-update." .. type .. " " .. file)

-- 改进后: (同一目录下的安全原子替换)
luci.sys.exec("cp -f /tmp/ssr-update." .. type .. " " .. file .. ".tmp && mv -f " .. file .. ".tmp " .. file)
```

## 5. 诊断日志与验证矩阵
本修复处于 Bash 底层环境的命令升级，未引入显式高层日志（与 B-167 沿用同样的 `[UPDATE-B167-②]` 校验记录），属于逻辑执行范畴的静默加强防线。

## 6. 回归测试
- [x] 断电沙盘推演验证: 若在 `cp` 时断电，原始 `file` 安全无恙（仅多出无用 `.tmp`），重启不受影响。若在 `mv` 时断电，系统调度保证要么是原文件，要么是新文件。从根源 100% 根除截断损坏。
